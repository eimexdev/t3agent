# Parker/eimexdev `t3agent` vs. Ben’s Hermes provider

Audited July 25, 2026 from:

- Parker/eimexdev: [`eimexdev/t3agent` at `dcfb3af20`](https://github.com/eimexdev/t3agent/tree/dcfb3af20)
- Ben: [`pingdotgg/t3code` branch `experiment/hermes-provider` at `c696e04e8`](https://github.com/pingdotgg/t3code/tree/c696e04e8)

This is a source audit, not a live usability test. “Implemented” means code and usually focused tests exist; UX judgments are inferences from those sources. Relative to their respective upstream bases, Parker’s branch changes 143 files with about 18,796 additions; Ben’s changes 98 files with about 15,017 additions.

## Executive verdict

These implementations have optimized different halves of the problem.

**Parker/eimexdev has the stronger Hermes product.** `t3agent` treats Hermes as the primary product and T3 as its durable conversation surface. It has much more ambitious conversation UX: a flat agent-oriented shell, Hermes session browsing/import/fork/lineage, Hermes-authoritative titles, command discovery and argument hints, per-session model and reasoning controls, images, voice notes and transcription state, context usage, and proactive/background/cron delivery. The product intent is explicit in the [architecture](https://github.com/eimexdev/t3agent/blob/dcfb3af20/docs/architecture/t3-agent.md#L5-L27).

**Ben has the stronger provider integration and operational story.** His branch makes Hermes a manageable T3 provider with multi-instance setup, one-time enrollment, long-lived credential issuance, outbound WebSocket connectivity, version/status reporting, revocation/removal, reconnect/liveness handling, and connection-replacement recovery. Its scope and topology are documented in the [gateway README](https://github.com/pingdotgg/t3code/blob/c696e04e8/integrations/hermes-t3-gateway/README.md#L1-L62).

The ideal implementation is not a wholesale choice between branches. It is Parker’s Hermes-native conversation semantics and richer surface on top of Ben’s connection, enrollment, and instance-management substrate.

## Architecture and code quality

### Parker/eimexdev

The TypeScript domain modeling is strong. The bridge is a schema-first tagged protocol with branded identifiers and boundary validation rather than duplicated interfaces ([contract](https://github.com/eimexdev/t3agent/blob/dcfb3af20/packages/contracts/src/hermesBridge.ts#L1-L83)). Conversation lifecycle policy is extracted from the transport, has typed `HermesLifecycleError`s, serializes fork/rename work, and imports history through normal orchestration commands ([lifecycle](https://github.com/eimexdev/t3agent/blob/dcfb3af20/apps/server/src/provider/hermes/HermesConversationLifecycle.ts#L1-L173)). This aligns well with T3’s contracts/package ownership, typed-error, and explicit-concurrency standards.

The strongest architectural decision is authority: Hermes owns session context, titles, model validation, STT, cron, and agent behavior; T3 stores a visible projection. Child-copy imports avoid two gateways silently mutating the same session. That is a coherent domain model, not a collection of UI additions.

Reliability goes beyond happy-path streaming. The plugin maintains a bounded persistent ingress-idempotency ledger and turn-completion outbox, while request identity preserves enough resolver state for approvals/clarifications to survive a T3 restart ([operations notes](https://github.com/eimexdev/t3agent/blob/dcfb3af20/integrations/hermes/t3agent/README.md#L38-L41)). The implementation added 37 changed test files and roughly 6,959 added test lines.

The principal code-quality weakness is concentration. [`adapter.py`](https://github.com/eimexdev/t3agent/blob/dcfb3af20/integrations/hermes/t3agent/adapter.py) is about 3,037 lines and combines transport, idempotency/outbox persistence, Hermes private compatibility, model/reasoning controls, command discovery, media, session history/forking, titles, and delivery. [`HermesAdapter.ts`](https://github.com/eimexdev/t3agent/blob/dcfb3af20/apps/server/src/provider/Layers/HermesAdapter.ts) is about 1,225 lines. The tests reduce regression risk, but these are shallow module boundaries: Hermes upgrades and cross-branch review will be harder than necessary.

There is also some local Effect-style migration debt: public reusable effects such as `listSessions` and `reconcileTitles` are constructed with `Effect.gen(...).pipe(...)` rather than named `Effect.fn` callables ([lifecycle](https://github.com/eimexdev/t3agent/blob/dcfb3af20/apps/server/src/provider/hermes/HermesConversationLifecycle.ts#L149-L173)). This is a standards issue, not evidence of incorrect behavior.

### Ben

Ben’s server architecture is stronger around transport ownership and provider administration. The contract explicitly separates browser-visible one-time enrollment from plugin credentials, models version incompatibility, distinguishes durable instance data from volatile connection state, and exposes `connectionGeneration` so reconnection logic does not depend on an unreliable connected/offline edge ([contract](https://github.com/pingdotgg/t3code/blob/c696e04e8/packages/contracts/src/hermesGateway.ts#L85-L139)). Those are excellent failure-aware choices.

The work is decomposed into connection registry, enrollment store, gateway broker, request correlator, adapter and service interfaces. That is more navigable than Parker’s Python concentration, although the [`HermesGatewayBroker.ts`](https://github.com/pingdotgg/t3code/blob/c696e04e8/apps/server/src/provider/Layers/HermesGatewayBroker.ts) is still about 1,240 lines, [`HermesAdapter.ts`](https://github.com/pingdotgg/t3code/blob/c696e04e8/apps/server/src/provider/Layers/HermesAdapter.ts) about 911, and the add-provider dialog about 937. Ben has the same “large orchestration shell” pressure, just with somewhat clearer service seams.

Ben’s compatibility audit is unusually candid about fragile upstream dependencies: exact-string suppression, steer acknowledgement matching, session-FIFO approvals, and missing public stream categories are all documented and pinned to an audited Hermes revision ([compatibility inventory](https://github.com/pingdotgg/t3code/blob/c696e04e8/integrations/hermes-t3-gateway/COMPATIBILITY.md#L49-L98)). The branch added 32 changed test files and roughly 6,310 test lines. Recent commits are dominated by race, liveness, reconnect, replacement and shutdown fixes, which indicates substantial adversarial testing of the connection lifecycle.

Ben also has Effect-style migration debt: several new long-lived effects and factories are direct `Effect.gen` values rather than named `Effect.fn` APIs. Again, this is chiefly maintainability/observability debt, not a correctness verdict.

## What Parker should port from Ben

1. **Outbound WebSocket transport.** Make Hermes dial T3 so remote use does not require exposing a Hermes HTTP listener or maintaining a tunnel. Preserve Parker’s delivery IDs, outbox, callback semantics, and child-copy session rules above the transport.
2. **Enrollment and credential lifecycle.** Replace four manually coordinated `.env` values with one-time pairing, direct issuance of a persistent credential, regeneration, rotation/revocation, and fail-closed version negotiation.
3. **Multi-instance domain model.** Remove the hard-coded `hermes` assumption. Adopt named instances and bind every conversation durably to its instance without silent fallback.
4. **Operational status UI.** Port connection state, last-connected time, Hermes/plugin/protocol versions, active sessions, upgrade-required state, and clear restart/reconnect guidance.
5. **Connection-generation semantics.** Re-establish session state whenever the underlying socket is replaced even if status never visibly passes through offline.
6. **Liveness and replacement tests.** Port the race cases around pings during handshake, delayed pongs, stale socket teardown, server shutdown, and active-session re-ensure.

These are architectural ports, not clean cherry-picks: Parker’s HTTP request/callback protocol and Ben’s bidirectional WebSocket protocol have different ownership models.

## What Ben should port from Parker

1. **Hermes-native session lifecycle.** Add session list/search, open existing T3 bindings, child-copy import of Discord/CLI/other gateway sessions, completed-run forks, and durable lineage. Do not attach a second UI to a live foreign session.
2. **Hermes-authoritative titles.** Disable independent T3 title generation for Hermes threads; accept rename only after Hermes does, then reconcile on reconnect.
3. **Command catalog and ghost hints.** Read Hermes commands/aliases/skills/plugins and retain T3’s fuzzy keyboard UX, while intercepting `/new`, `/sessions`, `/resume`, and `/fork` where thread identity changes.
4. **Model and reasoning controls.** Report authenticated provider/model inventory and supported reasoning efforts, then apply per-session overrides through Hermes’s own validation path.
5. **Attachments and voice.** Start with Parker’s bounded image contract and safe retrieval. Voice is valuable but larger: port the stable attachment identity, recording/draft UX, Hermes-owned STT, and correlated transcription events together.
6. **Durable ingress and delivery.** Adopt the persistent idempotency ledger and completion outbox so acknowledged requests and async/cron completion survive process restarts.
7. **Agent product surface.** Consider a provider-scoped “agent mode” rather than copying the whole fork: flat Hermes conversations, reduced repository chrome, lineage, session browser, and context meter can coexist with ordinary T3 provider mode.

Most of Parker’s UX should be ported as cohesive feature slices with contracts, server behavior, UI, and tests together. Cherry-picking isolated React components would import hidden assumptions about the single Hermes instance and `t3agent` product mode.

## Recommended convergence sequence

1. Stabilize a shared protocol/domain vocabulary for instance ID, session ID, delivery ID, capabilities, title authority, lineage, model selection, attachments, and reconnect resume.
2. Put Ben’s outbound connection and enrollment lifecycle underneath Parker’s durable idempotency/outbox semantics.
3. Split Parker’s Python adapter into protocol ingress, session repository, inventory/commands, media, lifecycle, and durable delivery modules while retaining the current tests as characterization tests.
4. Land session browser/import/fork/title semantics before voice; they establish the identity model every later UX feature relies on.
5. Add model/reasoning and command discovery.
6. Add images, then voice and proactive/cron delivery.
7. Offer the focused shell as a Hermes-provider presentation mode, keeping the underlying provider implementation usable in normal T3 Code.

The central caution is to avoid merging transports first and postponing identity semantics. Ben’s strongest code answers “how does this Hermes instance connect safely?” Parker’s strongest code answers “what exactly is a conversation, who owns it, and how should it feel?” A successful convergence needs both answers explicit from the start.
